1 Rôle dans la plateforme

iot-backend est le seul point d'entrée du navigateur. Il reçoit la télémétrie du boîtier via le broker MQTT, la valide, l'enregistre dans SQLite et la diffuse en temps réel au dashboard. Il orchestre aussi l'analyse par le service IA et relaie la vidéo de la webcam. Le navigateur ne contacte jamais directement MQTT ni FastAPI : toutes les routes passent par une session authentifiée.

2 Architecture

Le code suit la clean architecture. Les règles métier ne dépendent d'aucun framework, et les dépendances pointent toujours vers le centre : domain n'importe rien, application n'importe que domain, et presentation n'importe jamais infrastructure. Seul main.ts connaît les implémentations concrètes.

3 Flux de données

3.1 Ingestion de la télémétrie

  1. MqttDeviceGateway reçoit un message sur esp8266/donnees. parseTelemetryMessage le valide : nombres finis, presence booléen ou 0/1, ts en secondes Unix ou timestamp ISO, indicateurs booléens du boîtier, source live ou simulation. Un message invalide est rejeté en entier.
  2. RecordTelemetry détermine l'heure d'enregistrement avec resolveRecordedAt : l'heure de mesure est conservée si elle est plausible (au plus 60 s dans le futur, pas plus vieille que la rétention), sinon l'heure de réception est utilisée.
  3. La mesure est écrite dans la table readings avec sa source et ses indicateurs. DeviceState ne prend en compte que les mesures physiques les plus récentes : une mesure rejouée ou simulée ne remplace jamais l'état courant.
  4. L'événement reading est publié sur le bus interne. Le flux SSE le diffuse, l'AiCoordinator le place dans sa file et l'AlertDetector l'évalue.

3.2 Analyse IA

L'AiCoordinator envoie les mesures récentes (moins de 30 s, au plus 5 s dans le futur, ordre chronologique respecté par source) à POST /analyze, une à la fois pour préserver l'ordre des features temporelles. La file contient au plus 32 mesures ; en surcharge, la plus ancienne est abandonnée et dropped_samples est incrémenté. Les indicateurs de préchauffage et de validité excluent les canaux non fiables du lot envoyé. Le résultat validé est enregistré dans ai_predictions, puis publié en SSE (ai). Un sondage de /status toutes les 2 s alimente ai-status, même sans nouvelle mesure.

MQTT n'attend jamais l'IA. Si FastAPI est arrêté ou lent, le statut passe hors ligne, les mesures continuent d'être enregistrées et le dernier résultat reste consultable. Aucun résultat NORMAL ou SAFE n'est inventé.

3.3 Alertes

L'AlertDetector transforme les événements en alertes uniquement sur changement d'état :

  • intrusion : passage du PIR à « présence », pour une mesure physique récente (moins de 60 s) ;
  • visage inconnu : détection contenant un visage sans nom ;
  • boîtier hors ligne : aucune mesure physique depuis 30 s (vérification toutes les 10 s), une seule alerte par silence.

Les mesures et détections simulées ne déclenchent jamais de notification réelle.

4 Modèle de données

Le stockage utilise le module natif node:sqlite (aucune dépendance native à compiler), en mode WAL. Trois fichiers, configurables et ignorés par Git :

Les lectures et les prédictions IA partagent la même rétention (READINGS_RETENTION_DAYS, 7 jours par défaut), appliquée au démarrage puis toutes les heures. La provenance source permet d'exporter uniquement les mesures réelles pour l'entraînement du modèle IA.

6 Temps réel et vidéo

GET /api/stream ouvre un flux Server-Sent Events (text/event-stream). Chaque événement transporte l'objet JSON concerné : une lecture enregistrée (avec son id), une détection, une prédiction IA persistée ou le statut IA. Un commentaire de maintien est envoyé toutes les 15 s, et le flux est fermé quand la session expire : le client revient alors à l'écran de connexion. L'en-tête X-Accel-Buffering: no désactive la mise en tampon de nginx.

La vidéo ne passe jamais par SSE. /api/camera/stream relaie en flux continu le MJPEG du service IA, ou d'un service externe défini par VISION_STREAM_URL. Le relais préserve le Content-Type, ajoute le jeton du service IA côté serveur et annule la requête amont quand le navigateur se déconnecte.

7 Intégration du service IA

  • Contrat validé : infrastructure/ai/ai-contract.ts vérifie chaque réponse JSON de FastAPI avant persistance ou diffusion.
  • Authentification de service : si AI_SERVICE_TOKEN est défini, il est envoyé en Authorization: Bearer. Il n'est jamais transmis au navigateur.
  • Délais : 5 s par appel (AI_TIMEOUT_MS) ; 60 s pour le rechargement et l'enrôlement des visages.
  • Source de la caméra : VISION_STREAM_URL explicite prioritaire ; absent, le backend relaie AI_SERVICE_URL/stream.mjpg ; vide, la vidéo est désactivée.
  • Séparation réel / simulation : les prédictions conservent leur source ; une analyse simulée ne remplace pas l'état canonique de la webcam ni une analyse réelle récente.
  • Enrôlement facial : seule cette route accepte un corps JSON de 21 Mio, après vérification de la session. Limites : 5 photos, 5 Mio par photo et 15 Mio au total une fois décodées. Les noms sont normalisés et filtrés (séparateurs de chemin, noms réservés).

Le port Mailer a trois implémentations, choisies au démarrage : SmtpMailer si SMTP_HOST est défini (STARTTLS exigé hors TLS implicite), OutboxMailer si MAIL_OUTBOX_DIR est défini (fichiers .eml, mode test), sinon UnconfiguredMailer (aucun envoi, signalé dans l'interface).

9 Sécurité

  • Authentification : Better Auth, e-mail et mot de passe (12 caractères minimum), cookie de session HttpOnly, sessions de 8 h renouvelées toutes les heures. L'inscription publique est désactivée ; les comptes se créent en ligne de commande.
  • Limitation de débit : 100 requêtes d'authentification par minute et par IP, 5 tentatives de connexion par minute. L'IP est lue dans X-Forwarded-For, que le backend réécrit avec l'IP résolue selon TRUST_PROXY : un client ne peut pas la falsifier pour contourner le blocage.
  • Origines : CORS et origines de confiance limitées à FRONTEND_ORIGINS ; une connexion depuis une autre origine est refusée (403).
  • Taille des requêtes : 16 Kio par défaut ; 21 Mio uniquement pour l'enrôlement facial authentifié.
  • Secrets : BETTER_AUTH_SECRET obligatoire (≥ 32 caractères, refus de démarrer sinon) ; aucun secret dans le dépôt (.env ignorés, contrôle scripts/check-repository.py).
  • Traçabilité : chaque commande LED et chaque modification des paramètres sont journalisées avec l'e-mail de l'opérateur.
  • Conteneur : utilisateur non-root, système de fichiers en lecture seule, capacités Linux retirées, no-new-privileges, API non publiée (accessible seulement via nginx).

11 Tests et qualité

Les tests s'exécutent avec le runner natif de Node (node:test via tsx), sans broker, sans base persistante ni service IA réel :

  • domaine : horodatage plausible, commandes, règles de notification ;
  • application : cas d'usage, état de l'appareil, coordinateur IA, détecteur d'alertes et enrôlement facial, avec des faux adaptateurs en mémoire ;
  • infrastructure : parsing MQTT, dépôts SQLite en mémoire, client IA, contrats faciaux ;
  • présentation : routes IA et enrôlement (authentification exigée avant traitement, limites de taille).
