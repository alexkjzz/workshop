1 Rôle et principes

iot-frontend est le dashboard de supervision des opérateurs. Il affiche en temps réel les mesures et l'état du boîtier, les analyses du service IA et la webcam du serveur. Il permet aussi de gérer la reconnaissance faciale et de régler les notifications.

  • Un seul interlocuteur : l'application n'appelle que /api/* sur la même origine. Elle ne contacte jamais MQTT, FastAPI ni la caméra directement.
  • Aucune donnée inventée : une mesure absente, périmée ou invalide s'affiche comme inconnue, jamais comme un zéro ou un état normal.
  • Pas de dépendance graphique lourde : graphiques en SVG natif, icônes en ligne, aucune bibliothèque de composants.

2 Architecture

L'application suit la même clean architecture que le backend. Les composants React ne connaissent que des ports, c'est-à-dire des interfaces. Les implémentations concrètes sont instanciées une seule fois dans main.tsx et injectées par un contexte React (ServicesContext). Remplacer le transport (REST, SSE) ou l'authentification ne touche donc pas à la présentation.

Le routage utilise le fragment d'URL (#/metrics, #/camera, #/settings), ce qui fonctionne derrière n'importe quel serveur statique sans règle de réécriture.

3 Flux de données

DonnéeMécanismeFréquence
SessionAuthService.getSession() au démarrage, puis à chaque 401à la demande
État MQTT et dernière mesure physiqueGET /api/statustoutes les 2 s
Historique des mesuresGET /api/readings?limit=150 puis événements SSE readinginitial + temps réel
Analyses IA/api/ai/history et /api/ai/latest, puis SSE aiinitial + temps réel
Disponibilité IA, webcam, visagesSSE ai-status et GET /api/ai/statustemps réel + toutes les 5 s
Détections vision externesGET /api/vision puis SSE visioninitial + temps réel
VidéoBalise image sur /api/camera/stream (MJPEG)flux continu
  • Un seul EventSource (/api/stream) transporte les quatre types d'événements.
  • Fusion sans doublon : l'historique et le direct sont fusionnés par identifiant, triés par heure de mesure et bornés à 150 mesures (environ 5 minutes) et 50 analyses. Une mesure arrivée en retard prend sa place chronologique.
  • Reconnexion : après une coupure réseau, l'historique est rechargé pour récupérer les événements manqués. Si le serveur ferme le flux (session expirée, redémarrage), la session est revérifiée et le flux rouvert après 5 s.
  • Pas de régression : une réponse HTTP plus ancienne ne remplace jamais un état SSE plus récent.
  • Démarrage de la webcam : startVisionAndWait envoie start, puis interroge /api/ai/vision/status chaque seconde (20 s maximum) jusqu'à l'état running. Le flux vidéo n'est ouvert qu'à ce moment, avec une URL unique à chaque tentative.

5 Règles d'affichage

  • État du boîtier : sans mesure physique depuis 30 s, tous les états passent à « Inconnu ». Les indicateurs absents (préchauffage, capteur en erreur) restent inconnus.
  • Graphiques : une interruption de plus de 10 s entre deux mesures coupe la courbe au lieu de relier les points ; une mesure isolée est affichée comme un point.
  • Analyses IA : une analyse réelle récente (moins de 30 s) est prioritaire sur une analyse simulée. Les données de démonstration portent la mention SIMULATION. Une couverture incomplète affiche « Analyse partielle » et un niveau INDÉTERMINÉ plutôt que SAFE.
  • Vision : une détection de plus de 5 s n'est plus présentée comme courante ; un visage inconnu est signalé.
  • Erreurs : un 401 renvoie à l'écran de connexion ; les messages du serveur sont affichés tels quels dans la zone concernée.

6 Interface et accessibilité

  • Thème : clair ou sombre, il suit le système jusqu'au premier choix, puis le mémorise (localStorage). public/theme-init.js l'applique avant le premier affichage pour éviter un flash. C'est un fichier externe, pour rester compatible avec la CSP.
  • Couleurs : jetons CSS communs (index.css) pour les deux thèmes ; une couleur d'état est toujours accompagnée d'un texte, jamais seule.
  • Responsive : grilles adaptatives jusqu'à 320 px de large ; les tableaux larges défilent dans leur propre conteneur.
  • Accessibilité : focus clavier visible, libellés ARIA sur les boutons à icône, légendes cachées sur les tableaux, zones aria-live pour les messages, animations désactivées si le système le demande.
  • Graphiques : SVG avec ligne de 2 px, aplat léger, grille discrète, infobulle et réticule au survol ; le tableau des dernières mesures sert d'alternative textuelle.

7 Sécurité

  • La session est un cookie HttpOnly géré par Better Auth : il n'est pas lisible par le JavaScript de la page.
  • Aucun secret ni URL interne (FastAPI, broker, jeton IA) n'est présent dans le code client.
  • En production, nginx applique une Content Security Policy stricte (default-src 'self', frame-ancestors 'none'), X-Frame-Options: DENY, X-Content-Type-Options: nosniff et Referrer-Policy: no-referrer.
  • Les photos d'enrôlement sont vérifiées côté client (format, taille, nombre) pour un retour immédiat. Le serveur refait toutes les vérifications, qui seules font foi.

8 Build, déploiement et tests

npm run dev      # Vite, /api relayé vers http://127.0.0.1:3001
npm test         # règles du domaine et adaptateurs (runner natif de Node)
npm run lint     # oxlint
npm run build    # tsc -b puis vite build vers dist/

Production : l'image Docker compile l'application puis la sert avec nginx-unprivileged (utilisateur non-root, port 8080). nginx relaie /api/ vers le backend sur le réseau interne, avec une limite de taille élargie uniquement pour la route d'enrôlement facial.
